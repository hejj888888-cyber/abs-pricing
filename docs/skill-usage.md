### 1.4 为什么不能"硬凑"一个

老师明确列了一条否决项：**未真正调用 Skill、仅凭主观感觉拼凑内容，不视为完成作业。** 反向的坑同样存在——拿一个不相关的 Skill 硬套（比如用 `china-dcf` 去"估值"ABS 分层），在说明文档里一眼就能被看穿，而且会连带削弱 GAP 分析的可信度。

所以本项目的写法是：**如实说明群库的能力边界，用它擅长的那一段（审计、展示、数据），把不擅长的那一段（定价）自己补上。** 这本身就是"人机协同"的一个真实案例——不是所有事都能买到现成 Skill。

## 二、自研 Skill：`abs`

**状态：已完成并跑通**

### 做了什么

把"消费金融 ABS 分层定价"这一件事封装成可复用的 Python 包，输入一个 JSON 参数文件，输出三情景定价结果与 Markdown 报告。四个模块对应定价流程的四个步骤，另加一个结构反解模块：

| 模块 | 职责 | 关键函数 |
|---|---|---|
| `abs/pool.py` | 资产池参数与摊还假设 | `Pool.annuity_payment()` / `smm()` / `mdr()` |
| `abs/cashflow.py` | 逐月现金流引擎 | `build_schedule()` |
| `abs/waterfall.py` | 分层瀑布与触发 | `run_waterfall()` |
| `abs/pricing.py` | 票面反解与收益指标 | `solve_coupons()` / `irr()` / `tranche_metrics()` |
| `abs/structure.py` | 最小次级厚度反解 | `min_subordination()` |

### 怎么做的（可复现的步骤）

1. **先定接口，再写实现**：先写 `cases/*.json` 的参数结构，确定"一个案例需要哪些数"，再倒推代码需要哪些函数。这一步避免了写到一半发现参数不够用。
2. **按层验证**：每写完一层，单独跑一次小检查（见 `docs/design-notes.md` 第一节的验证清单），不做"全部写完再调试"。
3. **守恒校验前置**：`check_conservation()` 写在主流程里，每次运行强制校验，残差大于阈值就报警。这是最有效的一处防错设计。
4. **口径反复核对**：中途犯过一次错——判断"夹层是否受损"时只比了静态厚度，得出"极端情景下夹层安全"的结论；但实际跑出来次级损失 39%，说明超额利差在起作用。这条错误保留在报告第五节，作为"静态厚度 ≠ 实际损失"的说明。

### 自研过程中的三个判断

- **要不要用 pandas**：不用，理由见设计笔记第三节。
- **票面正算还是反解**：反解，理由见设计笔记第二节。
- **压力情景设几档**：最初两档（基准/压力），发现压力情景下次级零损失、区分度不足，改为三档并加大极端情景的违约倍数，才让分层保护的作用显现出来。

## 四、两条路径的关系

群 Skill 库覆盖的是投行的**通用环节**——读材料、查数据、审模型、出材料、做展示。它没有覆盖**结构化融资的定价内核**，因为这类能力属于少数机构的专有模型，不会以通用 Skill 的形式流通。

于是本项目的分工是：

- **群 Skill 负责"外围"**：模型审计（04）核对口径、报告模板（99）做成可访问网页、数据查询（35）尝试外部对标。
- **自研 `abs` 负责"内核"**：现金流引擎、瀑布分配、票面反解、厚度反解——这四件事群库里找不到替代品。

**这正是老师说的"人机协同"的真实形态**：不是让 AI 什么都做，而是先摸清工具库的边界，把边界内的事交给现成工具，边界外的事自己造。承认"库里没有"，比硬套一个不相关的 Skill 更接近真实工作场景。
