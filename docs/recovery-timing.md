## 一、做了什么

把 `abs/cashflow.py` 里「核销后固定滞后 6 个月、一次性回收」改成**显式事件调度**，
并开放 `Pool.recovery_distribution` 作为月度分布开关。

| 文件 | 改动 |
|---|---|
| `abs/cashflow.py` | `pending = [(核销月, 核销额)]` → `recovery_events: {到期月: 到账额}`；删掉尾部补记循环与有 bug 的 break 判断 |
| `abs/pool.py` | 新增 `recovery_distribution: tuple = ()` 与 `recovery_weights()`；`from_dict` 解析 |
| `cases/*.json` | 两单 pool 显式写 `"recovery_distribution": []`，`param_sources` 标为「假设」 |
| `scripts/run_case.py` | `PARAM_LABELS` 与 `param_table` 支持该参数；新增报告「二之三、回收时间分布」 |
| `tests/test_recovery.py` | 9 项新测试（49 → 58） |

核心代码（`cashflow.py`）：

```python
# 当期核销按分布排入未来各月的回收事件。排在 pop 之前，是为了让
# k=0（核销当月即回收）也能计入本月；one-hot 时只有 k=lag 一项。
if co > 0:
    for k, w in enumerate(rec_weights):
        if w > 0.0:
            t = m + k
            recovery_events[t] = (recovery_events.get(t, 0.0)
                                  + co * rec_rate * w)

# 本月应到账的回收款，可来自多个不同月份核销的叠加
recovery = recovery_events.pop(m, 0.0)
```

索引 `k` 表示「核销发生月 + k」。`recovery_weights()` 在分布为空时返回
`[0] * lag + [1]`，即第 6 月一次性到账的 one-hot 向量。

## 二、开工前发现的四个问题，逐个怎么关掉的

| # | 问题 | 解决方式 |
|---|---|---|
| 1 | **「只改时序、不改总量」的前提不成立**。回收款是循环期可购买资金的一部分，改到账月份会改购买额、队列规模、后续利息与核销，即改总量。第 2 周账龄曲线的两遍跑法不能套用。 | 不消除这个机制（它是真实的），而是把它**量出来**：报告二之三给出累计放款倍数对照，并在本节明确写清不能套用两遍跑法。基准仍用定点滞后，保证对表口径不变。 |
| 2 | **`pending` 是全局聚合、不分队列**，且 break 只看 `pending[-1][0] + lag`，另有一段单独的 tail 补记循环。分布一长就会漏记或提前退出。 | 改成 `recovery_events` 字典；主循环一直跑到事件表清空才 break（条件 `live <= 1e-6 and not recovery_events`），删掉 tail 补记循环与旧 break；`end` 额外留出 `len(rec_weights)` 个月。 |
| 3 | **队列寿命只有 5–8 个月**（`(1−核销率)/月还款率`），滞后已 6 个月，把现金流往后摊会落在余额耗尽之后。 | 回收侧已彻底解决：事件按到期月排程，余额归零后照常入账，`test_tail_recovery_is_not_truncated` 用 `lag=20` 的极端构造验证累计回收款一分不丢。核销侧的同类问题在第 5 周由「总量/时序分离」修复（见 `docs/loss-conservation.md`）。 |
| 4 | **参数出口不同步**：`Pool.from_dict`、报告参数表、case 来源标注、CSV、术语映射。 | 全部同步；`param_table` 对 tuple 特判，显示「定点滞后（未启用分布）」或「自定义 N 期权重」；`param_sources` 标为假设，报告第一节自动计入假设参数项。 |

关于第 3 条要诚实：**这次只解决了回收侧的截断**。W2 的核销账龄曲线在第 5 周由
「总量/时序分离」一并解决了截断问题，但**基准仍为 `enabled: false`，理由已更换**：
不是「会被截断」，而是公开报告只提供静态池图形、没有逐月数据点，`tau`/`k` 无法精确取得。
详见 `docs/loss-conservation.md` 第八节。

## 三、为什么回收时序不是中性的

```
核销发生 → 回收到账 → 计入循环期可购买资金 → 新增队列 → 继续核销 → 再产生回收
                              ↑______________________________|
```

`cashflow.py` 的现金守恒约束里：

```python
cash = cum_gross_principal + cum_recovery + sched + recovery - cum_purchased
purchase = min(reinvest * (sched + recovery), max(cash, 0.0))
```

`recovery` 直接进购买资金池。所以把同一笔回收从第 6 月挪到第 1–6 月，
循环期每月的可买资金都变了，队列成立时间变了，后续利息与核销也跟着变。
**这是循环购买结构的内生反馈，不是 bug，但不能像账龄曲线那样假设总量守恒。**

对照一下第 2 周：核销时序改的是「损失在哪个月确认」，累计核销总量被
`loss_weights()` 强制守恒，所以能用「先定总量、再分发」的两遍跑法。
回收时序改的是「现金哪个月到账」，而到账时间在循环结构里是内生变量。

## 四、显式假设声明（必须写清）

评级报告中债资信《表15：压力测试的基准条件和加压幅度》只给出两项：

- 核销后回收率：鼎柚 3.31% / 够花 2.78%
- **回收周期 6 个月**（原件用词，不是「回收滞后」）

原件**没有披露回收款在 6 个月内如何分布**，也没有「回收滞后」这个词。
`cases/README.md` 早已注明：`recovery_lag_months = 6` 是对「回收周期」的
**语义映射**，引用时不得写成「披露了回收滞后假设」。

因此：

- 默认 `recovery_distribution = []`（第 6 月一次性到账）是与披露口径一致的映射；
- 报告二之三里的「均匀铺开」「前高后低」「后高前低」三种形态，**全部是本模型
  显式引入的假设**，只用于敏感性分析，**不得引用为披露值**，也不得拿去和
  行业做法做「谁更准」的比较——老师要的是讲清对方的方法论，不是拿自己
  假设的分布冒充对方的。

## 六、结果：影响小到可以忽略

报告二之三的四种形态（固定滞后 / 均匀 / 前高后低 / 后高前低）：

| 案例 | 优先A WAL 极差 | 次级实现收益率极差 | 累计放款倍数极差 |
|---|---|---|---|
| 鼎柚 | 0.0001 年（约 0.04 天） | 0.04 pp | 3.3444x → 3.3464x（0.0020x） |
| 够花 | 0.0001 年（约 0.04 天） | 0.03 pp | 2.4484x → 2.4495x（0.0011x） |

方向与机制一致（回收前置 → 更早形成购买力 → 累计放款略增），但**量级可忽略**。
原因是核销后回收率只有 3.31% / 2.78%，回收款占资产池现金流的比重极低，
即使把到账从「第 6 月一次性」改成「1–6 月铺开」，循环期可购买资金的变化也只有万分之几。

**这属于「做了才发现没那么重要」的一类发现，如实记录。** 原计划 W3 的验收标准
「优先档 WAL 变化可解释」成立，解释就是：**变化接近零，因为回收款太小**。
若未来补一只回收率显著更高的产品（车贷 ABS 有抵押物），这一步才可能变得重要——
这也给第 7 周「第三单对照」提供了一条选型理由。
